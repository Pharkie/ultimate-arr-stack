## Deploying to the NAS

**The rule (no exceptions): every code change — even a trivial patch image bump — MUST be tested on the NAS and confirmed working BEFORE it reaches `main`.** There is no "trivial" fast-path that skips NAS testing.

This is delivered **branch-first** (resolves the old "test before commit" vs "deploy via git only" tension — confirmed by the user 2026-06-19). **Native git can't be installed on the NAS's OS** (`apt-get install git` fails on unmet deps tangled with unrelated vendor-pinned packages — never force it with `apt --fix-broken install`, that risks cascading into Ugreen's pinned packages). Real git still works there via a containerized `alpine/git` image bind-mounted onto the deploy path — bootstrapped 2026-08-15, `origin` points at the fork. Deployment is `git pull`, not file copying:

1. Make the change locally on a **feature branch**, commit, and push the branch.
2. Sync the branch to the NAS with `./scripts/sync-nas.sh` (checks out and fast-forwards to your current local branch on the NAS through the containerized git — never `.env`/config/volumes, those aren't tracked), then recreate the affected service(s) via compose (never SCP loose files, never ad-hoc `docker run`).
3. **Verify on the NAS:** container healthy, API/UI responds, migration clean, and `npm run test:e2e` where relevant.
4. Only once it's confirmed working → **merge the branch to `main`** (locally or via `gh pr merge`), then sync `main` to the NAS. A local merge auto-syncs via the `post-merge` hook (`./setup-hooks.sh`); a `gh pr merge` is remote-side and fires no local hook, so immediately follow it with `git fetch origin main && ./scripts/sync-nas.sh` (from a checkout of `main`) — do this every time, not just when asked. Nothing untested ever reaches `main`.
5. If it fails verification → fix on the branch and re-verify, or discard the branch. Re-sync `main` to the NAS with `./scripts/sync-nas.sh` to bring it back.

**Automated alternative:** `.github/workflows/nas-auto-deploy.yml` (`workflow_dispatch`, manual trigger only — added 2026-08-16) runs steps 1-4 above end-to-end: bats → connect to the NAS over Tailscale → back up config volumes (GFS-tiered retention, see `docs/BACKUP.md`) → sync the dispatched branch to the NAS → recreate the changed service(s) → wait for health → `npm run test:e2e` on the NAS → merge to `main` → sync `main` to the NAS. Any failing step stops the pipeline before main is touched, same guarantee as the manual flow. Requires one-time secret setup (`TS_AUTHKEY_CI`, `NAS_SSH_HOST`, `NAS_SSH_USER`, `NAS_SSH_KEY` — see `docs/BACKUP.md`'s *Automated Pre-Deploy Backup* section).

Worth remembering generally: a bats/test suite written and only ever run on a maintainer's already-configured machine can quietly assume local state that a clean CI checkout won't have — worth an explicit pass over any test suite before wiring it into CI for exactly this reason.
- Run 2 ([31945201657](https://github.com/leonardoazeredo/ultimate-arr-stack/actions/runs/31945201657)) got past bats and appeared to get past "Connect to Tailscale" and "Configure SSH to NAS", but failed at "Back up config volumes (GFS retention)": `ssh: connect to host *** port 22: Connection timed out`, exit 255, after ~2 minutes stuck on the OS-default TCP connect timeout. Digging into the logs found the earlier "Configure SSH to NAS" pass was a **false positive**: its `ssh-keyscan` retry loop (`for i in 1..10; do ssh-keyscan ... && break; sleep 3; done`) had no check after the loop, so it exited 0 whether or not any attempt actually reached the NAS — the ~80s gap before the next step lines up with all 10 attempts running to exhaustion without ever getting a host key. So this run never actually established SSH connectivity from the ephemeral GitHub-hosted runner to the NAS over Tailscale at all; the underlying "why" (route propagation delay, DERP/NAT-traversal issue from a non-LAN peer, something else) is still open — `tailscale status` locally showed neither peer has ACL tags, so a tag-based ACL restriction isn't the obvious explanation. **Fixed the false-pass** in PR #22: the keyscan loop now hard-fails with a clear error if it never gets a key, dumps `tailscale status`/`tailscale ping` output for diagnosis, and every real `ssh` call in the workflow now carries `-o ConnectTimeout=15` so a genuine failure surfaces in ~15s instead of ~2 minutes. This run was dispatched against `main` itself (no compose diff), so even a clean run would only have verified connectivity, not the compose-recreate path — do a run against a branch with a real compose change once connectivity is confirmed working.
- Snag worth remembering generally: a step that "succeeds" because a retry loop has no post-loop failure check can mask a real problem for several steps until something downstream finally trips over it — worth grep'ing any `for ... do cmd && break; done` pattern for a hard failure check after the loop, not just inside it.
- Run 3 ([31945945854](https://github.com/leonardoazeredo/ultimate-arr-stack/actions/runs/31945945854)), the first run with #22's diagnostics, showed the real root cause behind Run 2's connectivity failure: after 10 straight `ssh-keyscan` failures, `tailscale ping` succeeded immediately via a **direct** connection — the WireGuard peer-to-peer path just hadn't been established yet when raw TCP tools tried it; `tailscale ping` actively forces/confirms that handshake, plain TCP connects don't wait for it. Same diagnostics also showed the fixed Tailscale hostname colliding with a still-registered offline device from a prior run, silently getting suffixed (`-1`). **Fixed** in #24: `tailscale ping -c 1` before each `ssh-keyscan` attempt to warm the route, and a per-run-unique hostname (`gh-actions-arr-stack-${{ github.run_id }}`).
- With connectivity solid, later runs reached "Recreate affected services" / "Wait for container health" and surfaced two more live-NAS issues, fixed directly on the NAS (no PR — not compose/repo changes): a UGOS firewall rule was blocking inbound Tailscale traffic to the SSH/Docker ports the workflow needs, and `cloudflared` was stuck in a restart crash-loop consuming NAS resources during the health-check wait. Both fixed live and persisted through NAS-side config, not tracked in this repo.
- **npm doesn't exist on the NAS OS at all** (only a stripped internal Node.js runtime for UGOS's own admin panel, `/usr/bin/node` v18.20.4, no `npm`/`nvm`/`opkg` anywhere) — `npm run test:e2e` in the original plan (step 3 above) can't run there directly. **Fixed** in #25 by containerizing the e2e suite (`tests/e2e/Dockerfile`, extends the pinned Playwright image + `docker.io` CLI so `tests/e2e/helpers.ts`'s `DOCKER_AVAILABLE` gate can reach the NAS's real daemon via a bind-mounted socket), matching this repo's existing `alpine/git` pattern for tools the NAS OS lacks. `--network host` so `localhost:<port>` URLs resolve to the NAS's own published ports. Along the way: `npm ci` fails (`package-lock.json` is gitignored, never committed) — switched to `npm install`, which necessarily floats dependency versions on every run.
- That float bit back in run [31959525960](https://github.com/leonardoazeredo/ultimate-arr-stack/actions/runs/31959525960): `npm install` resolved `@playwright/test` to `1.62.1`, but the Dockerfile's pinned base image only bundled `1.50.0`'s browser build, failing every UI-screenshot test with `browserType.launch: Executable doesn't exist`. **Fixed** by running `npx playwright install chromium` at container *runtime* (after `npm install`), so the browser always matches whatever version npm actually resolved instead of trying to keep a Dockerfile pin and a floating range in lockstep.
- Run [31948292004](https://github.com/leonardoazeredo/ultimate-arr-stack/actions/runs/31948292004) then isolated 2 Traefik `.lan` macvlan-reachability e2e failures (`EHOSTUNREACH 192.168.8.250`) as the only remaining blocker, unrelated to the deploy pipeline itself. Root cause: a Linux host can never reach its own macvlan-networked containers, by kernel design — not fixable from inside the test container. **User chose to fix it at the infra level** rather than skip the tests. **Fixed** live on the NAS: a macvlan shim interface (`ip link add macvlan-shim link eth0 type macvlan mode bridge`, IP `192.168.8.251/32`) plus a host route to Traefik's macvlan IP (`192.168.8.250/32`) via that shim, persisted through a `@reboot` crontab entry (idempotent — checks the link exists before recreating it). No PR — NAS-side infra only.
- That reachability fix uncovered a real (not test-infra) bug: Radarr's and Sonarr's `/api/v3/health` reported all indexers unavailable. `/api/v3/indexer/test` (which re-tests with the actually-stored credentials, unlike the cached `health` endpoint) revealed genuine `401 Unauthorized` responses — Prowlarr's `Applications` sync pushes its own API key into Sonarr/Radarr's stored indexer config at setup time but never re-pushes if Prowlarr's key later changes, so 4 indexer entries (Radarr ids 2,3; Sonarr ids 2,3) were holding a stale key. **Fixed** by writing Prowlarr's current key into all 4 entries directly via `PUT /api/v3/indexer/{id}`; confirmed via `/api/v3/indexer/testall` (all valid) and `/api/v3/health` (clean on both apps). No PR — live app-config fix, not a repo file. This is the same credential-propagation coupling class of bug tracked more generally in the (separate, not-yet-executed) Terraform/devopsarr plan.
- With the indexer fix confirmed (run [31968133243](https://github.com/leonardoazeredo/ultimate-arr-stack/actions/runs/31968133243): 36 passed, 1 failed, 3 skipped — down from 3 failed), the one remaining failure was `sonarr.lan`'s Traefik-routing test: `getaddrinfo ENOTFOUND sonarr.lan`. Root cause: the NAS's UGOS-managed system resolver only points at the router, which has no `.lan` knowledge (that's Pi-hole's job, bound to `NAS_IP:53` specifically); the test's *initial* request connects by IP with a spoofed Host header, but the app's login-redirect `Location` header forces a real hostname lookup that the system resolver can't satisfy. **Fixed** in commit `cf33237` by adding `--dns "$NAS_IP"` to the e2e container's `docker run`.
- That fix (verified in run [31968540414](https://github.com/leonardoazeredo/ultimate-arr-stack/actions/runs/31968540414)) resolved the `ENOTFOUND`, but the same test then failed a different way: the redirect-follow request to `sonarr.lan` returned the **NAS's own UGOS admin-panel HTML** instead of Sonarr's login page. Root cause, confirmed via `node -e "require('dns').lookup('sonarr.lan',{all:true},...)"` on the NAS: dnsmasq (Pi-hole's backend) deliberately answers AAAA queries for `.lan` domains with the literal address `::` (see `pihole/dnsmasq.d/02-local-dns.conf.example`'s `address=/lan/::` — required so musl/Alpine containers like Gluetun don't hard-fail on AAAA NXDOMAIN elsewhere in the stack; not a bug, not something to change globally). Node's default `verbatim` DNS ordering returns both records; Linux's `connect()` treats a destination of `::` as `::1` (loopback), which under `--network host` lands on the NAS's own loopback-bound UGOS service instead of failing outright.
- Two attempted fixes both looked right in isolation but didn't actually work: `NODE_OPTIONS=--dns-result-order=ipv4first` (commit `964d5e1`) and `--add-host sonarr.lan:<traefik-ip>` both fixed a plain `node -e "dns.lookup(...)"` call on the NAS, but run [31968968267](https://github.com/leonardoazeredo/ultimate-arr-stack/actions/runs/31968968267) failed identically with the `ipv4first` fix in place, and a direct on-NAS repro of the actual test with `--add-host` present failed too. Root cause of *that*: Playwright's `APIRequestContext` resolves hostnames via `dns.resolve4`/`resolve6` (the c-ares path), not `dns.lookup()` — bypassing both `/etc/hosts` and Node's `--dns-result-order` entirely, so neither workaround could touch it. **Actually fixed** by going back to the test's own stated design intent (`tests/e2e/networking.spec.ts`'s existing comment: "rather than relying on the test runner's own DNS resolution working") — the auto-followed redirect was the thing breaking that guarantee, not the DNS layer. Disabled `maxRedirects` and manually re-issue the follow-up request by path against `TRAEFIK_LAN_IP` with the same spoofed Host header, so the test never needs real DNS at all. Verified directly on the NAS (both `sonarr.lan` and `jellyfin.lan` passing) before pushing as commit `a42cb93`, which also simplifies the e2e workflow step back down (`--dns`/`--add-host` no longer needed by anything in the suite).
- Snags worth remembering generally: (1) a test that "passes" because it got *some* HTTP 200 back is not proof it hit the right backend — worth asserting on response content, not just status code, exactly what caught this one. (2) DNS bugs can masquerade as app/routing bugs one layer up — the UGOS-HTML response looked like a Traefik or Sonarr problem until the raw `dns.lookup()` output made the real answer obvious. (3) A fix verified against a raw `node -e` one-liner is not the same as a fix verified against the actual library call site — Playwright's own resolver behaves differently from Node's default, and two rounds of "looks fixed" only turned out true once tested against the real test file, not a proxy for it. (4) When the infra-level fix keeps needing another infra-level workaround bolted on, that's a signal to check whether the *test's own design* already has an answer — this one explicitly said it wanted to avoid DNS, and the actual fix was making the auto-redirect behavior match that stated intent, not deeper DNS plumbing. (5) `scp` failed opaquely (`No such file or directory`) against the NAS's BusyBox `sftp-server` despite correct destination permissions — worked around by piping content through `ssh ... 'cat > dest'` instead, which doesn't depend on the SFTP subsystem.

`./scripts/sync-nas.sh` only pulls files — it never recreates containers. After any sync that touches a compose/service file, still recreate that service manually via its own compose file. Every containerized-git invocation on the NAS needs `-c safe.directory=/repo` (git only honors `safe.directory` via `--global` config, never per-repo, so this can't be set once and forgotten) — `leoleg`'s `arrgit` bash alias on the NAS bakes this in for ad hoc use.

**NEVER pass `--remove-orphans` to any `docker compose` command on the NAS.** The stack's services are split across multiple compose files sharing one project name, so compose treats every container from the *other* files as an orphan and deletes them all (this took out 11 containers on 2026-08-01). Likewise, only ever recreate a service via the compose file that defines it — e.g. traefik must go through `docker-compose.traefik.yml` or it loses its `traefik-lan` macvlan and every `.lan` URL dies. See `docs/TROUBLESHOOTING.md`.

Back up a service's config volume before any version bump with a DB migration (`docker run --rm -v <vol>:/src:ro -v <dir>:/bak alpine tar czf /bak/<svc>-config-backup-<stamp>.tgz -C /src .`). Never `docker stop` + ad-hoc `docker run` against a live container's static IP to test — apply the change through compose so the test reflects the real config.

## Tests

Run `npm test` (bats + Playwright) after any change to Docker Compose files, service config, networks, or ports. All tests must pass. `npm run test:bats` is fast, static, and needs no NAS/Docker access — it validates compose files themselves (no duplicate ports/IPs, pinned images, no secrets, `.env.example` in sync, pre-commit hook actually installed) and should catch config bugs before they ever reach the NAS. `npm run test:e2e` (Playwright, run on the NAS itself for full coverage) is split by domain under `tests/e2e/`: UI screenshots, API assertions, VPN egress/leak/killswitch checks, DNS/Traefik routing, addon coverage (Decypharr/Magnetio/stremio-jellyfin), and Gluetun zombie-container resilience checks. Don't hardcode a test count in this doc — that's exactly how the old "14 tests" claim went stale; describe categories instead.
