the audited record: what shipped, where the plan was wrong and why, the

- **Recreating Tailscale node 1 severs every path to the NAS at once** — SSH

## Deploying to the NAS

**The rule (no exceptions): every code change — even a trivial patch image bump — MUST be tested on the NAS and confirmed working BEFORE it reaches `main`.** There is no "trivial" fast-path that skips NAS testing.

This is delivered **branch-first** (resolves the old "test before commit" vs "deploy via git only" tension — confirmed by the user 2026-06-19). **Native git can't be installed on the NAS's OS** (`apt-get install git` fails on unmet deps tangled with unrelated vendor-pinned packages — never force it with `apt --fix-broken install`, that risks cascading into Ugreen's pinned packages). Real git still works there via a containerized `alpine/git` image bind-mounted onto the deploy path — bootstrapped 2026-08-15, `origin` points at the fork. Deployment is `git pull`, not file copying:

1. Make the change locally on a **feature branch**, commit, and push the branch.
2. Sync the branch to the NAS with `./scripts/sync-nas.sh` (checks out and fast-forwards to your current local branch on the NAS through the containerized git — never `.env`/config/volumes, those aren't tracked), then recreate the affected service(s) via compose (never SCP loose files, never ad-hoc `docker run`).
3. **Verify on the NAS:** container healthy, API/UI responds, migration clean, and `npm run test:e2e` where relevant.
4. Only once it's confirmed working → **merge the branch to `main` through a pull request**, then sync `main` to the NAS. **`main` is protected** (`enforce_admins`: pull requests required, force-pushes and deletions refused, so it applies to admins too), which means the local-merge route is closed: a merge made locally cannot be pushed, and `scripts/post-merge` now says exactly that instead of failing vaguely. Land it like this:

   ```bash
   git push origin <branch>
   gh pr create --fill && gh pr merge <n> --squash     # or merge it in the UI
   git fetch origin main && git checkout main && git merge --ff-only origin/main
   ```

   That last line matters twice: `gh pr merge` is remote-side and fires no local hook, and the NAS pulls from `origin` — so an unsynced merge can never reach it. The `--ff-only` merge does fire `post-merge`, which now finds `main` level with `origin` and simply runs the sync; if the hook is not installed, run `./scripts/sync-nas.sh` yourself. Nothing untested ever reaches `main`, and nothing reaches the NAS that `origin` does not have.

   **That hook had never once run, from the day it was installed until 2026-08-31.** It derived the repo root from `${BASH_SOURCE[0]}`, which git sets to the path inside the git dir (`.git/hooks/post-merge`); bash does not resolve the symlink, so `git -C .git/hooks rev-parse --show-toplevel` fatalled, `|| true` swallowed the error, and an `exit 0` guard meant for "not a git repo" fired on every merge. `tests/hooks-installed.bats` passed the whole time — it asserted the symlink existed, never that the hook did anything. `tests/nas-sync.bats` now runs the hook against a throwaway repo with a real origin and asserts on what happened.
5. If it fails verification → fix on the branch and re-verify, or discard the branch. Re-sync `main` to the NAS with `./scripts/sync-nas.sh` to bring it back.
6. **Always return the NAS to `main` when you stop working on a branch, even mid-task.** A NAS left checked out on a feature branch is indistinguishable from a deployed one — nothing in the UI, `docker ps`, or any health check reveals it, and the branch's config is fully live in the meantime. On 2026-08-27 a NAS left on `feat/pi1-pi2-split` pointed gluetun's `DNS_ADDRESS` at a Pi-hole that had never been deployed to pi2, which crash-looped the VPN and killed all downloads for 38 hours before anyone noticed. Full writeup in `docs/TROUBLESHOOTING.md`. When diagnosing anything stack-wide, check `git rev-parse --abbrev-ref HEAD` on the deploy path **first**.

**Automated alternative:** `.github/workflows/nas-auto-deploy.yml` (`workflow_dispatch`, manual trigger only — added 2026-08-16) runs steps 1-4 above end-to-end: bats → connect to the NAS over Tailscale → back up config volumes (GFS-tiered retention, see `docs/BACKUP.md`) → sync the dispatched branch to the NAS → recreate the changed service(s) → wait for health → `npm run test:e2e` on the NAS → merge to `main` → sync `main` to the NAS. Any failing step stops the pipeline before main is touched, same guarantee as the manual flow. It also refuses to start on a branch with no open PR: `main` is protected, so the job could not merge what it had just deployed. Requires one-time secret setup (`TS_AUTHKEY_CI`, `NAS_SSH_HOST`, `NAS_SSH_USER`, `NAS_SSH_KEY` — see `docs/BACKUP.md`'s *Automated Pre-Deploy Backup* section).

`./scripts/sync-nas.sh` **exits non-zero and says `NAS NOT synced`** when it cannot do its job — unreachable NAS, a local commit `origin` does not have, or a NAS that did not end up on the intended commit *and branch*. **NEVER pass `--remove-orphans` to any `docker compose` command on the NAS.** The stack's services are split across multiple compose files sharing one project name, so compose treats every container from the *other* files as an orphan and deletes them all (this took out 11 containers on 2026-08-01). Never `docker stop` + ad-hoc `docker run` against a live container's static IP to test — apply the change through compose so the test reflects the real config.

## Tests

Run the bats suite after any change to Docker Compose files, service config, networks, or ports. All tests must pass.

**Use `./tests/run-tests.sh` as the entry point, not `npm test`.** `npm` is a convenience wrapper, not the tool — `run-tests.sh` bootstraps bats from the vendored `tests/bats-core` submodule and needs no npm at all. This matters because the machines that most need to run it may not have npm: pi1 (the deploy host) does not, and the NAS has no npm whatsoever. A mandate naming `npm test` reads as a blocking toolchain gap on those hosts when the suite in fact runs fine.

The bats half is fast, static, and needs no NAS/Docker access — it validates compose files themselves (no duplicate ports/IPs, pinned images, no secrets, `.env.example` in sync, pre-commit hook actually installed) and should catch config bugs before they ever reach the NAS. One exception: `tests/network-segmentation.bats` asserts **live** router behaviour (the VLAN20 -> VLAN10 allow-list) rather than file text, because nothing checking only compose text would ever have caught the unrestricted forward that a manual audit found. It must run from a host with a VLAN20 address (pi1); everywhere else — CI, the NAS, another VLAN — it skips with a reason instead of failing. Its denied-port set is not hardcoded: it is derived at run time from what the NAS is actually listening on (wildcard and VLAN10-address binds only, so loopback- and tailnet-only sockets never pad it) minus the allow-list. That kills two failure modes at once — a probe can never "pass" against a port that was simply closed, and a service added on a new port is covered the moment it starts listening rather than whenever someone remembers to edit the test. Port 53 is asserted over **both** transports, because `vlan20-to-pihole-dns` is a `tcpudp` rule and a TCP-only probe would pass while UDP resolution — the transport DNS actually uses — was broken. One gap is stated in the file rather than papered over: Traefik has no denied-port assertion, because probed from inside VLAN10 it accepts 80 and 443 and nothing else, so any such assertion would be a test that cannot fail. The Playwright e2e half (`npm run test:e2e` locally, or the containerised runner on the NAS — see the deploy section above, the NAS has no npm) is split by domain under `tests/e2e/`: UI screenshots, API assertions, VPN egress/leak/killswitch checks, DNS/Traefik routing, addon coverage (Decypharr/Magnetio/stremio-jellyfin), and Gluetun zombie-container resilience checks. Don't hardcode a test count in this doc — that's exactly how the old "14 tests" claim went stale; describe categories instead.

**Proving a guard can fail is not optional here, and it is now mechanical.** `./tests/mutation/run-mutations.sh` reintroduces a recorded defect, asserts the file actually changed, and requires the named test to go red — see `tests/mutation/README.md`. Four tests in this repo were merged as coverage while being incapable of failing, and reading them caught none of them. Run it after touching any guard, and add a corpus entry with any new one. It is deliberately not part of `./tests/run-tests.sh`: it runs the suite twice per mutation. Its companion `./tests/mutation/run-generated.sh` is the discovery half — universalmutator (containerised, pinned) perturbs `scripts/lib/` systematically and anything the suite fails to kill lands in `tests/mutation/survivors.tsv` for hand triage; it is non-blocking and always exits 0, because equivalent mutants can never be killed by anything. It sweeps Python as well as shell, picking the ruleset from the file extension, and drops mutants that land inside a comment or docstring — those can never be killed and once buried 144 real findings under prose edits in a single module.

**The Python half of the stack has its own oracle.** The three `scripts/lib/*.py` modules were heredocs inside their shell scripts until 2026-09-01; they are real modules now, tested with `./tests/toolkit/pytest.sh` (containerised — pi1 and the NAS have no pytest, and pi1 has no pip either). `tests/python-suite.bats` is what runs it from the bats suite, and it also asserts that every module in `scripts/lib/` has a test file, so a new one cannot arrive untested. `pytest.sh` exits **77**, never 0, when docker is unavailable: an absent oracle and a passing oracle must not be the same observable result.

**`docs/TEST-HARDENING-LOG.md`** is the audited record of the 2026-09-01 hardening pass (`86d5fcf`) — read it before touching `scripts/post-merge`, `scripts/sync-nas.sh`, `scripts/arr-backup.sh`, or `tests/mutation/`. It records which guards here turned out to be *incapable of failing*, and the shell and test traps that produced them; §8 is the list. §5.4 covers the later `scripts/lib/*` coverage pass — every check the pre-commit hook sources now has its own bats file, and nine defects were found by writing those tests. Anything that drives a *real* operational script must go through `tests/helpers/stubs.bash`: it puts stub executables on `PATH` (a shell function is not enough — `timeout` execs) and refuses any argv carrying a mutating verb, so a test can never reach a live `docker restart` on the NAS.
